## 📋 通用工作流程检查清单

### 任务开始前

- [ ] **理解任务本质**
  - [ ] 明确任务目标是什么？
  - [ ] 理解业务逻辑和背景
  - [ ] 识别影响范围（哪些文档会受影响？）

- [ ] **搜索先行**
  - [ ] 遇到不确定信息，先搜索文档
  - [ ] 查找已有相关信息
  - [ ] 建立信息地图（相关文档位置）

- [ ] **影响分析**
  - [ ] 列出所有可能受影响的文档
  - [ ] 识别文档间的依赖关系
  - [ ] 建立修改优先级

---

### 任务执行中

- [ ] **系统性执行**
  - [ ] 按优先级逐个修改
  - [ ] 确保修改的一致性
  - [ ] 记录修改内容

- [ ] **实时验证**
  - [ ] 每修改一个文档，验证是否正确
  - [ ] 检查是否有语法错误
  - [ ] 检查格式是否统一

---

### 任务完成后（强制执行）

- [ ] **完整性验证**
  - [ ] 所有相关文档都已修改？
  - [ ] 所有提到该信息的地方都已更新？
  - [ ] 没有遗漏的文档？

- [ ] **一致性检查**
  - [ ] 所有文档中的信息是否一致？
  - [ ] 是否有矛盾的地方？
  - [ ] 优先级、费用、定位是否统一？

- [ ] **反思与改进**
  - [ ] 这次犯了什么错误？
  - [ ] 为什么会犯这个错误？
  - [ ] 下次如何避免？
  - [ ] 更新错误清单和最佳实践

## 🚨 错误模式库（Error Pattern Library）

> **说明**：记录常见错误模式及其根本原因，帮助AI识别和避免类似错误。  
> **更新原则**：每发现一个新错误，必须分析根本原因并更新此库。

---

### 类型A：信息获取错误（Information Retrieval Errors）

#### 错误A1：留空让用户填写

- **错误表现**：遇到不确定信息，留空或写"[待填写]"
- **根本原因**：懒惰思维，不愿意搜索
- **正确做法**：先搜索文档，查找已有信息
- **检查方法**：遇到不确定信息时，先grep或codebase_search
- **触发信号**：看到"[待填写]"、"[用户补充]"等占位符
- **错误严重度**：中（影响用户体验）

---

### 类型B：系统性思维错误（Systemic Thinking Errors）

#### 错误B1：只改明确指出的文件

- **错误表现**：用户说改3个文档，就只改这3个
- **根本原因**：局部思维，缺少全局视野
- **正确做法**：系统性检查所有相关文档
- **检查方法**：使用检查清单，列出所有可能受影响的文档
- **触发信号**：批量修改、术语统一、业务逻辑调整
- **错误严重度**：高（导致不一致）

#### 错误B2：没有同步更新相关文档

- **错误表现**：修改了A文档，但B文档也提到同样信息，没改
- **根本原因**：缺少影响范围评估
- **正确做法**：修改前先搜索，找出所有相关文档
- **检查方法**：使用grep或codebase_search全局搜索
- **触发信号**：修改核心概念、术语、数据、流程
- **错误严重度**：高（导致信息冲突）

---

### 类型C：理解与验证错误（Understanding & Validation Errors）

#### 错误C1：不理解业务逻辑就改

- **错误表现**：机械执行，不理解为什么这样改
- **根本原因**：缺少业务理解，只知道"做什么"不知道"为什么"
- **正确做法**：先理解业务逻辑，再执行修改
- **检查方法**：修改前先问"为什么"，理解后再改
- **触发信号**：涉及业务规则、核心流程、关键数据
- **错误严重度**：高（可能破坏业务逻辑）

#### 错误C2：没有验证完整性

- **错误表现**：修改后没有检查是否遗漏
- **根本原因**：缺少验证机制
- **正确做法**：建立检查清单，逐个验证
- **检查方法**：使用grep搜索所有提到该信息的地方
- **触发信号**：大范围修改、批量操作
- **错误严重度**：中（可能有遗漏）

---

### 类型D：设计意图错误（Design Intent Errors）⭐ 最严重

#### 错误D1：没有先理解设计意图就动手操作

- **错误表现**：看到文件系统的"问题"，立即尝试修复，不先理解设计意图
- **典型案例**：看到两个04目录，立即想改序号，而不是先读README理解设计
- **根本原因**：
  1. 以现状为准，而不是以设计文档为准
  2. "看到症状就开药"，而不是"先诊断再治疗"
  3. 缺少"设计意图"这个强制思考点
- **正确做法**：
  1. 先阅读README.md，理解正确的设计
  2. 以README为准，而不是以当前文件系统为准
  3. 分析问题的本质（是设计问题还是执行问题）
  4. 再提出解决方案
- **检查方法**：
  - 遇到目录结构问题时，先读README.md的"目录结构"部分
  - 确认正确的设计意图
  - 检查Git历史，了解目录来源
  - 再决定是合并、移动还是删除
- **触发信号**：
  - 目录结构调整
  - 文件重命名
  - 架构修改
  - 看到"不符合规范"的文件/目录
- **错误严重度**：严重（可能破坏整体设计）
- **预防机制**：强制思考点（见.cursorrules）

#### 错误D2：基于假设而非验证

- **错误表现**：基于"我认为应该是XX"直接操作，没有验证假设
- **根本原因**：缺少假设验证步骤
- **正确做法**：
  1. 明确列出假设
  2. 验证假设（查设计文档、Git历史）
  3. 确认假设正确后再操作
- **检查方法**：任何基于推测的操作，都要先验证
- **触发信号**：出现"应该是"、"可能是"、"估计是"等不确定词汇
- **错误严重度**：高（假设错误导致方向错误）

---

### 类型E：操作顺序错误（Operation Sequence Errors）

#### 错误E1：先动手后思考

- **错误表现**：看到任务就立即开始执行，不先思考
- **根本原因**：缺少前置思考步骤
- **正确做法**：
  1. 先理解任务本质
  2. 分析影响范围
  3. 设计解决方案
  4. 再执行操作
- **检查方法**：执行前先完成"强制思考点"
- **触发信号**：所有高风险操作
- **错误严重度**：高（方向错误，返工成本高）

## 📊 错误严重度分级

**严重（Critical）**：
- 错误D1：没有先理解设计意图
- 错误D2：基于假设而非验证
- 影响：可能破坏整体设计，返工成本极高

**高（High）**：
- 错误B1：只改明确指出的文件
- 错误B2：没有同步更新相关文档
- 错误C1：不理解业务逻辑就改
- 错误E1：先动手后思考
- 影响：导致不一致或逻辑错误，需要返工

**中（Medium）**：
- 错误A1：留空让用户填写
- 错误C2：没有验证完整性
- 影响：影响用户体验或有遗漏，可补救

## 🛡️ 错误预防机制

### 机制1：强制思考点（最重要）

**触发条件**：
- 结构性修改
- 业务逻辑修改
- 大范围修改

**强制执行**：
- 理解设计意图
- 验证假设
- 评估影响范围

**工具支持**：
- .cursorrules中的强制思考点机制
- 系统指令4.2中的设计意图理解步骤

### 机制2：检查清单

**使用时机**：
- 每次任务开始前
- 每次任务完成后

**检查内容**：
- 是否理解设计意图？
- 是否验证假设？
- 是否评估影响范围？
- 是否完整验证？

### 机制3：反思机制

**执行时机**：
- 每次任务完成后
- 发现错误后

**反思内容**：
- 犯了什么错误？
- 根本原因是什么？
- 如何避免？
- 更新错误模式库

## 🔄 错误模式更新流程

**发现新错误时**：

1. **记录到反思日志**（`04_反思日志.md`）
   - 错误表现
   - 根本原因
   - 改进措施

2. **分析错误类型**：
   - 属于哪个类型？（A/B/C/D/E）
   - 是新的错误模式吗？

3. **更新错误模式库**：
   - 如果是新模式，增加新错误
   - 如果是已有模式，补充案例

4. **更新预防机制**：
   - 是否需要新的检查清单？
   - 是否需要新的强制思考点？

**何时查阅**：

## ✅ 最佳实践清单（持续积累）

### 实践1：修改业务优先级时
1. 先搜索所有提到"优先级"、"P0"、"P1"的文档
2. 建立修改清单
3. 按优先级逐个修改
4. 最后全局搜索验证

### 实践2：修改费用数据时
1. 先搜索所有提到该费用的文档（如"3-5%"）
2. 检查是否有其他表述方式（如"3%-5%"）
3. 统一修改
4. 验证是否还有遗漏

### 实践3：修改业务定位时
1. 先搜索所有提到该定位的文档（如"杀手锏"）
2. 检查业务详解、话术、培训文档
3. 统一修改
4. 更新记忆口诀

### 实践4：修改JD时
1. 检查JD库、面试评估表、面试提纲
2. 检查BOSS直聘JD
3. 检查进度追踪器中的任务状态

### 实践5：遇到不确定信息时
1. 先搜索文档（grep或codebase_search）
2. 如果找不到，再问用户
